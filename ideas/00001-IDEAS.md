# Gatekeepr Appeal Plan: Differentiate From UserCheck

## Summary
- Do not compete with UserCheck by becoming "another disposable-email checker." Their advantage is focus and proof; your advantage is broader signup-risk intelligence across email, domain, IP, and user agent.
- Reposition Gatekeepr as a lightweight signup abuse engine for indie SaaS products: "stop fake signups before they consume credits, trials, or support time."
- Use an open-core model for trust and distribution: open-source the engine/rules/datasets, sell the hosted API, managed list refreshes, uptime, and simpler operations.

## Key Changes
- Positioning and messaging:
  - Rewrite the homepage around one narrow use case: protecting free trials, waitlists, communities, and account creation.
  - Replace generic phrases like "block fake users" with outcome copy: save credits, reduce spam accounts, protect onboarding funnels.
  - Add a "Who it's for" section for indie SaaS, AI tools, community products, and marketplaces.
  - Add a comparison section: Gatekeepr vs disposable-email-only tools, emphasizing multi-signal detection and explainable flags.

- Proof and trust:
  - Add 1-3 real case studies, even if small, with concrete outcomes like fewer fake signups, reduced abuse, or cleaner free-tier usage.
  - Publish operational proof you can support: latency, uptime target, number of checks, list refresh cadence, and sample detections.
  - Add privacy/data-retention, security, and reliability pages.
  - Replace vague FAQ claims with precise, defensible statements.

- Conversion and packaging:
  - Replace the "contact us to upgrade" flow with visible pricing tiers and a self-serve upgrade path.
  - Keep the free plan, but define paid request buckets and feature gates clearly.
  - Make the primary CTA "test your signup flow" and the secondary CTA "read the rule engine / docs."
  - Add stronger onboarding: copy-paste examples for Next.js, Express, Node, and webhook/server-action flows.

- Product experience:
  - Make the demo feel like a decision tool, not just raw JSON.
  - Show triggered rules, why they matter, and a recommended action: allow, review, or block.
  - Add threshold presets in the dashboard for common products: free trial, waitlist, community, marketplace.
  - Add recent-check history and explainability so users can trust the score quickly.

- Open-core strategy:
  - Open-source the core detection engine, public rule definitions, and list-refresh logic after cleanup.
  - Keep the hosted layer differentiated through managed hosting, ready-to-use API, refreshed datasets, dashboards, and support.
  - Add `LICENSE`, `CONTRIBUTING.md`, `SECURITY.md`, public setup docs, and a short architecture overview.
  - Remove production-only workflows and secret-writing steps from the public repo before publishing.

## Public Interfaces
- Keep the existing API endpoints stable.
- Improve the response UX by exposing clearer explainability fields if needed, such as per-rule reason text and recommended action.
- No pricing or positioning work should require a breaking API change.

## Validation
- Landing page success criteria:
  - A new visitor should understand the target user, use case, proof, pricing, and integration path within 30 seconds.
  - A new developer should reach a first successful check in under 10 minutes.
- Product success criteria:
  - Free users should see an actionable decision, not just a score.
  - Upgrade intent should not depend on manual outreach alone.
- Open-source success criteria:
  - The public repo should be installable locally, readable, and credible enough to earn trust from developers evaluating the hosted API.

## Assumptions
- Recommended strategy chosen: differentiate from UserCheck rather than compete head-on.
- Recommended monetization path chosen: open core with a hosted API.
- Recommended proof path chosen: case studies first, then broader operational metrics.
- Recommended audience chosen implicitly by this plan: indie SaaS builders and small teams who need simple signup abuse protection without building in-house fraud tooling.
